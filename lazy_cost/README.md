# lazy_cost：分层惰性步代价（给候选初始位姿排序）

联合布局 × 顺序反向搜索使用的 cost 工具，不是论文贡献。独立于 `slot_roadmap/` 和
`cost_module/`，只依赖 `curobo_bridge`（cuRobo 封装、IK、topp）和 `scenes/benchmarks`
（装配体模型）。

## 一步的 cost

零件 p 放在候选位姿 x、用抓法 g 时：

- 空手段：上一件撤离构型（或 HOME）→ prepick(x, g)
- 携物段：lift(x, g) → preins(g)

每段取"静止到静止、各关节速度和加速度受限"的时间，单位秒。候选的 cost 取所有抓法中的最小值。

## 四层（`cost.py`）

| 层 | 做什么 | 结果 |
|---|---|---|
| 1 硬剔除 | 这一步静态不稳定或插入被挡；悬停 / prepick / pick / lift（携物）/ preins（携物）构型碰撞；悬停→prepick 垂直下降、pick→lift 垂直抬起（携物，跳过开头 1/4：零件还贴着桌面）碰撞；携物时手持零件撞到手臂连杆 link2–link5（夹爪本来就接触，不查） | 删除这对（候选, 抓法）；全部抓法都删 → 删除候选 |
| 2 下界 | 每段 `max_j t_trap(|Δq_j|)`：每个关节至少要转过 |Δq_j|，任何路径都不会更快 | 每个候选都有值 |
| 3 直线检查 | 两段关节直线一次 GPU 批量查碰撞 | 没被挡：下界就是准确值；被挡：待确认 |
| 4 惰性精算 | τ = 第 K 小的已确定 cost；只对"有待确认段、且下界 < τ"的（候选, 抓法）按下界从小到大逐段调用 cuRobo（`refine.py`），每算一段更新 τ | 前 K 名及其顺序与"全部规划"一致 |

没精算的候选，下界已证明它进不了前 K，按下界排在后面。

## 验证

`exp_rack10.py --model {triangular_frame6, rack10}`，WRS 抓法 8 种，每个装配体 30 组密集杂乱场景，每组 12 个候选，K = 3。参照：对每个存活的（候选, 抓法）用顺序 cuRobo MotionPlanner 规划。

**只有零件做障碍（正常场景，2026-10-16，`_output/exp_*_partsonly_*.jsonl`，`--boxes 0,0 --crowd 0 --gap 0.03`，各 30 组）**

| 装配体 | 排序方式 | 第 1 名误差 ≤ 2% | 前 3 召回 | 平均遗憾 | 最大遗憾 | 每组用时（中位） |
|---|---|---:|---:|---:|---:|---:|
| 三角框架 | 惰性（含精算） | 100% | 0.97 | 0.0% | 1.4% | 1.7 s（精算 6 段） |
| | 只用下界 | 83% | 0.86 | 1.3% | 11.9% | 0.07 s |
| | 下界，被挡 × 1.25 | 77% | 0.82 | 1.4% | 8.4% | 0.07 s |
| | 全部规划（参照） | — | — | — | — | 14.5 s |
| rack10 | 惰性（含精算） | 93% | 0.90 | 0.2% | 2.3% | 0.8 s（精算 3 段） |
| | 只用下界 | 90% | 0.88 | 0.4% | 4.2% | 0.04 s |
| | 下界，被挡 × 1.25 | 77% | 0.81 | 1.1% | 6.8% | 0.04 s |
| | 全部规划（参照） | — | — | — | — | 26.9 s |

- 被挡比例：三角框架 77%（空手段 64%、携物段 44%），rack10 47%（31% / 23%）。三角框架的立柱粗高，已装零件和桌上零件都容易挡路。
- 但被挡大多只需小绕行：真实时间 / 下界，三角框架中位 1.012、p90 1.08、最大 1.22；rack10 中位 1.000、p90 1.02、最大 1.10。
- 只用下界时，30 组里分别有 23 组（三角框架）和 26 组（rack10）完全选对；选错的组都是"下界最小的候选恰好需要较大绕行"（例如下界 1.61 s、实际 1.93 s）。
- 固定的 × 1.25 惩罚在正常场景下反而更差：多数被挡的段并不慢。
- 参照里第 1、2 名常常只差几个百分点（中位 3–5%），cuRobo 自身约有 ±2% 的波动，所以 2% 以内的错位不算错误。

**重要更正：计时函数与参照的口径（2026-10-16 晚）**

1. 原计时函数（`curobo_bridge.assembly_demo.topp`）在弯曲路径上把切向和拐弯加速度分开限制，关节实际可达约 2 倍加速度，时间被低估，甚至低于下界。现改用 `timing.py` 的 TOPP：每个关节两部分加速度合起来受限，直线时等于下界。**本节之前所有实验里，被挡段的真实时间都被低估了。**
2. 参照真值的口径改为：**每段直线能走通就按直线执行（时间 = 下界），否则按 cuRobo 路径执行**。cuRobo 轨迹优化的路径并不直，用正确的计时后会比直线慢 2–17%；把能走直线的段也算成 cuRobo 路径，会让参照失真。

用新计时重跑"只有零件"的两组（`_output/exp_*_feat2_parts_*.jsonl`，各 30 组）：

| 计时方式 | 被挡段 真实 / 下界：中位 | p75 | p90 | 最大 |
|---|---:|---:|---:|---:|
| 旧计时（有误） | 1.021 | 1.064 | 1.120 | 1.49 |
| **新计时** | **1.229** | **1.360** | **1.470** | **1.76** |

新修正系数（`penalty_model.json`，非负最小二乘，1342 段被挡运动）：估计 = 下界 × (1 + 0.243 + 1.09 × 最大穿透深度[m])。只要被挡就约多花 24%，穿透越深再多一些。

| 装配体 | 排序方式 | 第 1 名误差 ≤ 2% | 前 3 召回 | 平均遗憾 | 最大遗憾 |
|---|---|---:|---:|---:|---:|
| 三角框架 | 只用下界 | 70% | 0.78 | 3.68% | 21.7% |
| | 下界 + 新修正 | 87% | 0.90 | 1.27% | 18.3% |
| | 惰性精算 | 97% | 0.97 | 0.47% | 13.9% |
| rack10 | 只用下界 | 83% | 0.89 | 1.68% | 18.3% |
| | 下界 + 新修正 | 93% | 0.92 | 0.47% | 9.6% |
| | 惰性精算 | 100% | 0.99 | 0.00% | 0.0% |

结论更新：下界对被挡段明显偏低（中位低约 20%），修正和惰性精算都更重要了；"下界很紧"只对直线可走的段成立。

**下界 + 被挡程度修正（不调规划器，2026-10-16，`analyze_penalty.py`，`_output/exp_*_feat_*.jsonl`）**

同一次碰撞计算顺便输出每条被挡直线的指标（`checker._blocked_features`）：碰撞比例、被挡区段、最大 / 平均穿透深度、撞的是机械臂 / 手持零件 / 要抓的零件、碰撞点高度。被挡段的估计 = 下界 × (1 + e)，e 由指标的非负线性组合拟合。

- 和"真实 / 下界"的秩相关：最大穿透深度最好（0.50–0.75），其次平均穿透、碰撞比例；撞的部位、高度作用很小。
- 排序（平均遗憾 / 最大遗憾）：

| 场景 | 只用下界 | 下界 × 常数 | 下界 + 线性修正 | 线性修正（用另一个装配体拟合） | 惰性精算 |
|---|---|---|---|---|---|
| rack10 只有零件 | 0.35% / 4.3% | 0.30% / 4.3% | 0.26% / 5.1% | 0.39% / 5.1% | 0.33% / 5.1% |
| rack10 密集 | 3.29% / 32% | 1.05% / 15% | 0.80% / 15% | 0.80% / 15% | 0.27% / 2.0% |
| 三角框架 只有零件 | 1.28% / 12% | 0.93% / 12% | 0.88% / 12% | 1.38% / 15% | 0.09% / 1.4% |
| 三角框架 密集 | 2.15% / 15% | 1.58% / 15% | 1.03% / 14% | 1.08% / 14% | 0.10% / 1.3% |

- 结论：修正能把平均遗憾降低约一半（密集场景最明显），但最大遗憾基本不变（12–15%），跨装配体拟合在三角框架上无效。修正适合用来给搜索排序，最终方案仍需对被挡段精算（搜索层面惰性验证）。

**精算轻量化（默认，2026-10-16，`bench_trajopt.py` + `_output/exp_*_partsonly_fast_*.jsonl`）**

精算原来用 `plan_cspace`：4 个种子，两轮 L-BFGS 各 100 次迭代，第二轮是时间最优微调。我们用 topp 重新计时，只需要路径形状，所以现在先跑**一轮、50 次迭代、2 个种子**（`trajopt_solver.solve_cspace(finetune_attempts=0, initial_iters=50)`，规划器建时 `num_trajopt_seeds=2`），失败时才退回完整规划。迭代次数必须是 25 的倍数；种子数只能在建规划器时设定。

单段对比（两个装配体各 40 个被挡段）：每段 76–78 ms（原来 289–473 ms）；topp 时间 / 原来：中位 1.000，p90 1.01–1.02，最大 1.04–1.08；80 段全部首次成功。25 次迭代时最大偏差达到 27%，不采用。

### 早期实验得到的结论（规则抓法，2026-10-15，数据已删除）

早期一轮 30 组实验用的是模型自带的规则抓法。原始数据已删除，具体数字不再引用，只保留与抓法来源无关、可以沿用的结论：

1. **下界是严格成立的**：33 个只算了下界的候选，cuRobo 参照时间 / 下界的最小值是 1.000，没有一例违反。
2. **下界通常很紧**：约 79% 的候选真实时间在下界的 2% 以内；约 15% 超过 10%，约 9% 超过 20%，最多 50%。只用下界排序的错误集中在这一成多"绕路代价大"的候选上，惰性精算正是用来纠正它们的。
3. **精算次数取决于"被挡"的候选数，而不是候选总数**：精算段数与被挡的（候选, 抓法）数相关系数 0.72，与存活候选数只有 0.40。平均只需全部规划 40% 的段数。
4. **快速精算有时会给出偏长的路径**：精算只做一次 TrajOpt 尝试，参照用完整 MotionPlanner。同一候选两者之比的 p5 是 0.89、中位 1.00、p95 1.02，即约 5% 的情况精算比参照慢 10% 以上。前几名很接近时会因此排错（参照中第 1、2 名相差不到 4% 的情况约占 21%）。可以考虑对前 K 名的精算多做一次尝试。
5. **时间主要花在精算上**：剔除约 80 ms、直线检查约 16 ms，精算每段约 230 ms（其中规划约 200 ms）。批量调用在本机上不摊薄开销（每个问题约 75 ms，且会补满整批），所以批大小取 1。
6. **在这种密集场景下，硬剔除会删掉很大一部分候选**：主要原因是 prepick 撞墙或箱子，其次是手指包住零件时撞到邻近物体、插入前姿态撞已装零件。30 组里有 8 组剩下不到 3 个候选，4 组全部被删。所以场景生成器偏密，正式实验需要控制障碍密度。

### 抓法与 IK 分支检查（`check_grasp_ik.py`，WRS 抓法，2026-10-16，`_output/check_grasp_ik.json`）

只算下界，不调 cuRobo，只有桌子和底座，8 根立柱 × 40 个候选。参照为 120 种覆盖性抓法 × 所有一致分支的最优值（近似"全部抓法"）。

- **IK 分支不是问题**：当前端点目录里 prepick / pick / lift 跳变超过 0.5 rad 的只占 0.7%；改成"同分支取最优"后结果几乎不变。
- **抓法选择影响很大**：同一个候选，不同抓法的下界最好与最差之比，中位 1.17（从 HOME 出发）/ 1.33（从上一件的撤离姿态出发），最大约 2。所以 cost 必须带入具体抓法，而且和上一步的撤离姿态有关。
- **3 种抓法不够，8 种基本够**：

| 抓法集合 | 可抓候选（参照 296） | 下界 / 参照 p50 / p90 / 最大 | 秩相关 | 前 3 重合 |
|---|---|---|---:|---:|
| 当前（3 种，只按装配位挑） | 241 | 1.06 / 1.29 / 1.78 | 0.80 | 0.71 |
| 两侧都可行的 3 种 | 267 | 1.05 / 1.23 / 1.78 | 0.84 | 0.71 |
| 两侧都可行的 8 种 | 292 | 1.01 / 1.12 / 1.32 | 0.97 | 0.79 |

（起点为上一件的撤离姿态；从 HOME 出发时规律相同，差距更小。）
